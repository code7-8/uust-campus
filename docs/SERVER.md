# Один сервер для всех устройств

Существующий API в `server/server.py` и SQLite сохранены. Android подключается к общему HTTPS-адресу через мобильный интернет или любую Wi-Fi сеть. Карта и встроенное расписание работают независимо от этого сервера.

## Развёртывание на Render

В репозитории есть `Dockerfile` и Blueprint `render.yaml`. Публичный сервер ещё не создан: рабочего адреса хостинга в исходниках нет.

1. В Render выберите **New → Blueprint**, подключите репозиторий и ветку `feature/public-backend-map-fixes` до её слияния. Проверьте план и диск перед созданием сервиса. Blueprint задаёт один экземпляр и постоянный диск 1 ГБ в `/data`.
2. Введите `ADMIN_USERNAME` и уникальный `ADMIN_PASSWORD` длиной 12–128 символов в настройках секретов. Не помещайте пароль в Git, Dockerfile или APK. Необязательное `ADMIN_NAME` задаёт отображаемое имя.
3. Запустите Deploy. Сервер установит Waitress, откроет `PORT` на `0.0.0.0`, создаст таблицы и первого администратора. Ручной ввод в облаке не нужен. Render автоматически задаёт `RENDER_EXTERNAL_URL`; на другом хостинге нужен `PUBLIC_URL`.
4. Откройте `https://<имя-сервиса>.onrender.com/v1/health`. Ожидается JSON с `ok: true`, `service: "UUST Campus"`, `setupRequired: false`. Health-check обращается к SQLite: недоступная база не считается здоровым сервисом.
5. На всех телефонах: **Профиль → Сервер команды → Проверить и подключить**. Введите корень HTTPS-сервера, например `https://uust-campus-ваше-имя.onrender.com`, **без `/v1`, `/v1/health` и внутреннего порта процесса**. Фактический адрес выдаст хостинг. На телефоне `localhost` обозначает сам телефон.
6. Войдите администратором. Остальные участники регистрируются и создают встречи; администратор выдаёт право публикации официальных событий. Проверьте публикацию на одном телефоне и «Я пойду» на другом, затем перезапустите сервис и убедитесь, что аккаунты, события и запись сохранились.

Render предоставляет HTTPS перед контейнером. SQLite обязательно хранится на постоянном диске: обычные файлы сервиса теряются при перезапусках/деплоях. Диск доступен на платном плане и привязан к одному экземпляру; обновление такого сервиса может ненадолго прерывать доступ. Это причина `numInstances: 1`, а не ограничение числа телефонов. См. [диски Render](https://render.com/docs/disks), [Docker](https://render.com/docs/docker), [health-check](https://render.com/docs/health-checks), [переменные платформы](https://render.com/docs/environment-variables).

Автоматический деплой при push выключен (`autoDeployTrigger: off`). Секреты администратора после первого успешного запуска можно удалить: существующий администратор сохраняется, пароль не сбрасывается. Если база потеряна, старт без начальных секретов завершится ошибкой вместо создания пустого публичного сервера.

## Переменные окружения

`.env.example` — образец. Python не загружает `.env` автоматически: задавайте переменные через хостинг, контейнер или оболочку. CLI `--host`, `--port`, `--data` переопределяют соответствующие настройки.

| Переменная | Назначение |
| --- | --- |
| `CAMPUS_ENV` | `production` для хостинга; по умолчанию `development`. |
| `HOST` | Адрес прослушивания, по умолчанию `0.0.0.0`. |
| `PORT` | Порт процесса: по умолчанию `8787`, в Blueprint `10000`. Внешний HTTPS обычно использует 443. |
| `DATABASE_PATH` | В production обязателен абсолютный путь на постоянном диске; в Blueprint `/data/campus.sqlite`. Локально — `server/data/campus.sqlite`. |
| `PUBLIC_URL` | Корень HTTPS-адреса без пути/параметров. Обязателен в production, если нет `RENDER_EXTERNAL_URL`. |
| `ADMIN_USERNAME` | Первый администратор: логин из 3–32 символов, латиница, цифры, `_.-`. Нужен для пустой базы. |
| `ADMIN_PASSWORD` | Секрет первого администратора, 12–128 символов в production. Нужен для пустой базы. |
| `ADMIN_NAME` | Отображаемое имя; по умолчанию логин. |
| `CORS_ORIGINS` | Дополнительные HTTPS origins браузеров через запятую. Публичный origin и Android `https://appassets.androidplatform.net` разрешены автоматически. Маска `*` запрещена. |
| `TRUSTED_PROXY` | По умолчанию пусто: forwarded-заголовки не учитываются. IP доверенного reverse proxy или `*` в изолированной сети хостинга. В Blueprint — `*`. |
| `TRUSTED_PROXY_COUNT` | Число доверенных прокси в цепочке; по умолчанию 1. |
| `THREADS` | Потоки Waitress: по умолчанию 8, максимум 64. Процесс и экземпляр сервиса — один. |
| `AUTH_RATE_LIMIT` | Попытки регистрации/входа за минуту с одного IP: по умолчанию 25. |
| `REQUEST_RATE_LIMIT` | Запросы API за минуту с одного IP: по умолчанию 300; health-check исключён. |
| `LOG_LEVEL` | `INFO` по умолчанию; также `DEBUG`, `WARNING`, `ERROR`. Приложение не журналирует пароли, токены, тела запросов и query strings. |

Waitress обрабатывает `X-Forwarded-For` и `X-Forwarded-Proto` только от доверенного прокси. При одном доверенном узле IP берётся с правого края цепочки: поддельный IP, дописанный клиентом слева, не меняет счётчик запросов. `TRUSTED_PROXY=*` допустим только за HTTPS-прокси, который перезаписывает/дополняет forwarded-заголовки, при закрытом от внешней сети порте Python. Для дополнительного CDN настройте фактическое количество доверенных узлов. [Настройки Waitress](https://docs.pylonsproject.org/projects/waitress/en/latest/reverse-proxy.html).

CORS не заменяет авторизацию. Публичная регистрация создаёт обычного участника; роль проверяется сервером. Лимит мест проверяется транзакцией SQLite. На аккаунт сохраняются до десяти активных сессий; выход отзывает текущую сессию.

## Другой HTTPS-хостинг или VPS

Нужны Python 3.10+, один постоянно работающий процесс, локальный постоянный диск и TLS-терминация хостинга/reverse proxy. Установите зависимости и используйте штатную команду:

```sh
python -m pip install -r server/requirements.txt
python server/server.py
```

Либо соберите `docker build -t uust-campus .` и запустите образ с переменными из секретного env-файла и постоянным volume в `/data`. Контейнер работает от UID 10001: при bind mount каталог должен быть доступен ему на запись. За reverse proxy на том же VPS публикуйте порт только на loopback: `-p 127.0.0.1:8787:8787`. Настройте сертификат домена и проксирование на этот адрес. Проверка сертификатов в Android остаётся включённой.

Не запускайте несколько реплик с отдельными SQLite-файлами: они создадут разные афиши и аккаунты. Не размещайте SQLite на NFS/сетевом диске. Для нескольких экземпляров потребуется отдельная СУБД; сейчас она не вводилась. `SIGTERM`/`Ctrl+C` завершают сервер, транзакции и WAL сохраняют данные при перезапуске.

## Данные и резервные копии

Существующая база совместима: таблицы не удаляются, добавляются только индексы. SQLite хранит аккаунты, хеши паролей и токенов, события и участников. Файлы базы, WAL и секреты исключены из Git и Docker build context.

Согласованная копия работающего сервера:

```sh
python server/server.py --backup /data/backups/campus-2026-09-30.sqlite
```

Команда использует SQLite Backup API, включая изменения из WAL, и отказывается перезаписывать существующий файл. Регулярно переносите копии в закрытое хранилище вне сервера. HTTP-эндпоинта выгрузки базы нет.

Для переноса с ноутбука создайте копию локальной базы, остановите целевой сервер и загрузите копию по `DATABASE_PATH`. Не подменяйте базу работающего процесса. При восстановлении переместите прежние `campus.sqlite`, `campus.sqlite-wal`, `campus.sqlite-shm` в отдельный закрытый архив, разместите копию и запустите сервер. В приложениях выберите новый HTTPS-адрес и войдите заново. Дополнительного администратора создаёт интерактивная команда `python server/server.py --init-admin` в приватной консоли сервера.

## Локальный запуск

Создайте виртуальное окружение, установите `server/requirements.txt`, запустите `start-server.cmd`. Скрипт предпочитает `.venv\Scripts\python.exe` и передаёт аргументы CLI. В режиме разработки первый запуск в интерактивном терминале предлагает создать администратора. Без терминала задайте переменные начального аккаунта.

HTTP разрешён только для прежних локальных адресов: `localhost`, `127.0.0.1`, `10.0.2.2`, `192.168.137.1`, `192.168.31.245`. Это не адреса публичного сервера. Android по-прежнему запрещает произвольный HTTP.

Браузерная страница сервера поддерживает аккаунты и общую афишу. Сервер не проксирует университетское расписание: Android использует прежний HTTPS API, а локальная полная веб-разработка — `tools/preview.py`. Афиша обновляется каждые 20 секунд. Создание, редактирование, удаление, запись и отмена требуют связи с общим сервером.

## Проверки

```sh
python -m unittest discover -s server -p "test_*.py" -v
npm ci
npm test
npm run validate:maps
npm run test:browser
```

Браузерные проверки используют установленный Chrome и создают временные базы и тестовые аккаунты. `PYTHON` указывает на интерпретатор с Waitress. Можно установить Chromium (`npx playwright install chromium`) и задать `PLAYWRIGHT_CHANNEL=chromium`. Проверяются два независимых браузерных профиля; HTTP-тесты моделируют разные IP за прокси, проверяют CORS, лимиты, перезапуск и восстановление SQLite.
